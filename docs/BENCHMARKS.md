# Checkout performance before and after the RabbitMQ timeline

## Workload and machine

Both snapshots ran on the same AMD Ryzen 3 5300U machine with Docker Desktop Linux engine 29.9.3, 8 logical CPUs and 3.51 GiB of Docker memory. k6 1.4.2 ran in Docker against an isolated stack. Each workload used one stocked SKU, one authenticated customer, unique checkout keys, and an approving payment simulator. There was no dispatch during traffic. The steady workload offered 20 orders per second for 300 seconds. The burst offered 100 orders per second for 30 seconds.

The Step 6 steady run overlapped other local verification. The snapshots also used different container builds and had no Git commit ID in this workspace. This is an observed comparison across builds. The measurements do not isolate RabbitMQ's overhead.

## What the numbers measure

Checkout p95 is measured at k6. Payment p95 is the interval from order creation to the saved confirmation event. The pending counts and drain times are calculated from the end of the k6 run, including any checkout requests that were still in flight at the end of the scheduled arrivals. Timeline lag measures each event from the stored order change to the stored projection. Timeline pending at run end counts event rows, including confirmations generated by outstanding payments as they later finish.

The steady target is at least 5,940 admissions out of 6,000 offered, p95 checkout within 500 ms, and no unexpected errors. The burst can explicitly reject excess load, with every admitted order reaching a terminal state. Review the actual sent count before assessing the offered rate.

The full steady and burst runs had zero capacity rejections, unexpected responses, dropped iterations, or unreconciled orders. The p95 for admitted checkouts therefore matches the overall checkout p95. Every order had one matching simulator approval and one unit reserved in both the hold and movement records. The 6,000 steady orders produced 12,000 matching timeline entries. The 3,000 burst orders produced 6,000.

| Step 8 workload | Oldest pending payment at run end | Timeline event lag p95 | Timeline entries delivered after run end | Timeline drain |
| --- | ---: | ---: | ---: | ---: |
| Steady | 0.386 s | 0.334 s | 17 | 0.359 s |
| Full burst | 44.884 s | 2.546 s | 3,000 | 85.812 s |

The steady run passed the 500 ms target. The full burst completed with matching records, and checkout took substantially longer than in the Step 6 burst. The payment backlog also took about 40 seconds longer to clear.

The two incomplete bursts dropped 58 and 90 k6 iterations respectively. They used 500 and 1,000 preallocated VUs, with maximums of 1,000 and 1,500. All admitted orders confirmed and reconciled in both attempts. The full burst used 1,800 preallocated VUs and a maximum of 2,200. Both retries used fresh stacks.

## Reproduce the current workload

```powershell
npm ci --prefix tests/e2e
./tests/recovery.ps1 -Benchmark
```

Use `-Workload burst` or `-Workload steady` to run one scenario. The script creates its own Docker project, confirms every admitted order, reconciles saved payment terms across both databases, matches the holds and movements to stock balances, and checks the staff timeline against the source order events. It emits JSON records with the exact image ID and measurements.
